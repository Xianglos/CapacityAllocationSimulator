## 1. 系统概述与技术选型

### 1.1 Demo 目标

| 编号 | 目标 | 验证内容 |
|---|---|---|
| D1 | 全链路跑通 | CSV 输入 → 需求展开 → 产能计算 → 工厂优先分配 → 交换优化 → 结论输出 |
| D2 | 业务规则正确 | C1–C7 硬约束 + S1–S5 策略规则可复现（见《业务建模.md》§5 及本设计新增 S5） |
| D3 | 结论可信 | 富余/缺口判定、四维缺口明细、设备/区域/工厂利用率 |
| D4 | 桑基图可见 | 品种→工序→设备→区域→完成/缺口 流向可直接浏览 |
| D5 | 优化可控 | 交换优化可启停、有时间熔断、优化耗时与效果可见 |

### 1.2 技术选型

| 项 | 选型 | 理由 |
|---|---|---|
| 演算引擎 | Java 17+（仅标准库） | 零依赖，`javac` 直接编译 |
| Web 层 | Node.js ≥ 16（仅内置 `http`/`fs` 模块，**无 npm 依赖**） | 一个 `server.js` 搞定静态页 + API，免 Express/构建工具 |
| 前端 | 单 HTML 页面（原生 JS + ECharts CDN，无框架无构建） | 打开即用 |
| 层间通信 | Node 以子进程方式调 Java **批处理 CLI**（`child_process.spawn`），经文件交换状态与结果（progress.json / result.json） | 避免自造协议，天然隔离两个运行时 |
| 数据存储 | CSV 文件（UTF-8 带 BOM，逗号分隔，首行表头） | 替代数据库表；Excel 可直接编辑 |
| 可视化 | 页面内嵌 ECharts 渲染桑基图；同时落盘 `sankey.html` 备独立打开 | 兼顾页面集成与文件留档 |
| 日志 | 控制台简单输出 + progress.json | 不引入日志框架 |

> CSV 兼容性：写入统一 UTF-8 with BOM（前置 `\uFEFF`），保证 Windows Excel 打开不乱码。

## 3. CSV 表结构设计（替代数据库表）

通用约定（适用于所有表）：

- 首行为表头，列名固定；多余列忽略，按表头名取值（列顺序无关）。
- 空行忽略；`#` 开头为注释行，忽略。
- 文本字段含逗号时用英文双引号包裹（解析器支持成对引号）。
- 编码类字段在主表中有唯一编码，被引用表存编码。

### 3.1 主数据表（data/master/）

#### ① product.csv —— 品种表

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| product_code | string(≤20) | 是 | **PK，唯一** | 品种编码，如 `P001` |
| product_name | string | 是 | 非空 | 品种名称 |

#### ② process.csv —— 工序表

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| process_code | string(≤20) | 是 | **PK，唯一** | 工序编码，如 `OP10` |
| process_name | string | 是 | 非空 | 工序名称 |

> 工序顺序由工艺路线表的 `seq` 逐品种表达，工序表本身不设全局序号。

#### ③ routing.csv —— 工艺路线表

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| product_code | string | 是 | **FK→product**，`(product, seq)` 唯一 | 品种 |
| process_code | string | 是 | **FK→process** | 工序 |
| seq | int | 是 | >0，同品种内不重复 | 工序顺序（从小到大流转） |

#### ④ equipment.csv —— 设备表（区域/厂区/出勤率/设备类型均为字段，**单表承载**）★v1.2.2 合并

> 原 v1.2 的 equipment / area / factory 三张表**合并为一张**：一台设备一行，其区域、厂区、出勤率、设备类型都是该行的字段。区域与厂区不再设独立主表，成为**由设备表去重派生的维度**（加载时在内存中构建 `区域→设备列表`、`厂区→区域列表` 派生视图）。

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| equipment_code | string(≤20) | 是 | **PK，唯一** | 设备编码，如 `M001` |
| equipment_name | string | 是 | 非空 | 设备名称 |
| equipment_type | string | 否 | - | 设备类型（描述性字段，暂不参与演算；预留按类型筛选/汇总扩展） |
| area_code | string(≤20) | 是 | 非空；同区域可含多台设备 | 所属区域编码（如 `A1`） |
| factory_code | string(≤20) | 是 | 非空；同厂区可含多个区域 | 所属厂区编码（如 `F1`） |
| attendance_pct | decimal | 是 | 0 < 值 ≤ 100 | 出勤率，百分数（`85.5` = 85.5%） |

```csv
equipment_code,equipment_name,equipment_type,area_code,factory_code,attendance_pct
M001,冲床01,冲压,A1,F1,90.0
M002,冲床02,冲压,A1,F1,85.0
M003,组装机03,组装,A2,F1,60.0
M005,组装机05,组装,A3,F2,95.0
```

> **一致性约束（跨行冗余的一致性由校验保证，V11）**：同一 `area_code` 必须对应同一 `factory_code`（区域不许跨厂区拆分）；同一区域出现不同厂区 → 校验错误。
>
> **工厂优先序约定（Demo 从简，待业务确认）**：**分配优先序 = factory_code 升序**（`F1` 先于 `F2` 先于 `F3`，编码即序号）——不再设独立 sort_no 字段。若某场景需要非字典序，改用带序编码（F10/F20）即可。工厂优先是策略（S5，见 §5.5），契约提供的 `factoryOrder` 即按此约定派生，未来算法可自行改变次序语义。

#### ⑤ process_equipment.csv —— 工序-设备对应表

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| process_code | string | 是 | **FK→process**，`(process, equipment)` 联合唯一 | 工序 |
| equipment_code | string | 是 | **FK→equipment** | 可加工该工序的设备 |

#### ⑥ process_time.csv —— 加工时间表（品种-工序）

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| product_code | string | 是 | **FK→product**，`(product, process)` 联合唯一 | 品种 |
| process_code | string | 是 | **FK→process**，且 ∈ 该品种工艺路线 | 工序 |
| minutes_per_lot | int | 是 | >0 | 单 Lot 加工分钟数 |

> 覆盖性约束：品种工艺路线中每道工序必须有加工时间记录，缺失在校验阶段报错（§7 V04）。
> **口径说明（重要，与 §5.6 打分公式相关）**：当前模型加工时间与设备/厂区无关（同品种同工序在任意设备上分钟数相同）。若业务实际存在厂区间效率差异，需将本表升级为按厂区区分的口径——见 §5.6 的公式影响说明。

#### ⑦ area_eligibility.csv —— 区域可加工性表（品种-允许区域）

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| product_code | string | 是 | **FK→product**，`(product, area)` 联合唯一 | 品种 |
| area_code | string | 是 | 值须在设备表 area 字段中出现过（V13） | 该品种允许生产（加工）的区域 |

> **缺省语义（Demo 约定，需业务确认）**：品种在表中**无任何记录** → 视为**允许所有区域**。
> 空集校验：品种有记录但与"工序-设备对应"求交后候选设备为空 → 允许加载，演算时按 Q6 口径判缺口（原因=`无可加工设备`）。

### 3.2 输入数据表（data/input/）

#### ⑧ lots.csv —— 月度 Lot 清单表（生管每月提供/编辑）

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| lot_no | string(≤30) | 是 | **PK，唯一** | Lot 编号 |
| product_code | string | 是 | **FK→product** | 品种 |
| qty_lots | int | 是 | >0 | Lot 数量（可 >1） |
| priority | int | 是 | ≥1，越大越优先 | 粗优先级（手动设定） |
| due_date | string(yyyy-MM-dd) | 否 | 合法日期或空 | 交期，仅展示不参与排序（Q5） |

#### ⑨ 演算月份 —— 非表，运行参数

不设日历表。演算月份作为运行参数传入（Web UI 输入框 / CLI `--month`），由 `java.time.YearMonth` 计算：

```
月度日历分钟 = yearMonth.lengthOfMonth() × 24 × 60
设备可用分钟 = round(月度日历分钟 × attendance_pct / 100)   ← 四舍五入取整（R7 分钟口径）
```

```
equipment（单表：设备+区域+厂区+出勤率+类型）
```

## 4. 领域模型（Java 类设计）

均为不可变 record（演算过程中的可变状态封装在引擎内部）。

```java
// model/ —— 与 CSV 表一一对应
public record Product(String code, String name) {}
public record ProcessStep(String code, String name) {}
public record RoutingItem(String product, String process, int seq) {}
public record Equipment(String code, String name, String type,        // ★v1.2.2 单表：
                        String area, String factory,                  //   类型/区域/厂区
                        double attendancePct) {}                      //   均为字段
public record ProcessEquipment(String process, String equipment) {}
public record ProcessTime(String product, String process, int minutesPerLot) {}
public record AreaEligibility(String product, String area) {}
public record Lot(String lotNo, String product, int qtyLots, int priority, String dueDate) {}

// 派生视图（加载时从 equipment.csv 去重构建，非 CSV 实体）★v1.2.2
//   Map<String, List<Equipment>> areaToEquipments   区域→设备列表（区域维度）
//   Map<String, List<String>>  factoryToAreas       厂区→区域列表（厂区维度）
//   Map<String, String>        areaToFactory        区域→厂区（V11 一致性校验的依据）
//   Map<String, Integer>       factoryOrder         厂区→优先序排名（factory_code 升序派生）

// 引擎内部结构
public record ProcessDemand(String lotNo, String product, String process, int seq,
                            int demandMinutes, List<String> candidateEquipments) {}
// ↑ 候选设备集合：C3/C4 静态过滤后的平铺列表；算法按工厂优先序自行分组（§5.5）

public final class CapacityAccount {          // 设备产能账本（可变，硬约束强制器）
    private final String equipment;
    private final int availableMinutes;
    private int usedMinutes = 0;
    public int remaining() { return availableMinutes - usedMinutes; }
    public boolean tryOccupy(int minutes) {   // C5+C6：整 Lot 校验，不可拆分
        if (remaining() >= minutes) { usedMinutes += minutes; return true; }
        return false;
    }
    public boolean release(int minutes) {     // ★新增：优化器迁出/回退用（平台控制，不越界）
        if (usedMinutes >= minutes) { usedMinutes -= minutes; return true; }
        return false;
    }
}

public record AllocationRecord(String lotNo, String product, String process, int seq,
                               String equipment, int demandMinutes, String status) {}
// status: ALLOCATED / GAP_LOT_STOP；Lot 终态由全部工序记录推导（全 ALLOCATED → 完成）

public record GapLot(String lotNo, String product, String gapProcess, String reason) {}
```

## 5. 演算引擎详细设计（业务模型与算法隔离）

### 5.0 分层架构与隔离原则

系统分三层，层间**只通过不可变数据契约**通信，具体算法与优化器均可替换：

```
┌────────────────────────────────────────────────────────────┐
│ 业务模型层（算法无关，平台组件）                              │
│   P1 需求展开 DemandExpander（候选设备静态过滤 C3/C4）        │
│   P2 产能计算 CapacityCalculator（R3/R5 初始账本）            │
│   硬约束强制器 CapacityAccount（C5/C6 整Lot校验；release 受控）│
├────────────────────────────────────────────────────────────┤
│          ▼ 统一契约① SimulationContext（§5.1）               │
│  ┌──────────────────────────────────────────────────────┐  │
│  │ 算法层（可替换，SPI）                                  │  │
│  │   interface AllocationAlgorithm（§5.2）               │  │
│  │   ├─ BestFitGreedyAlgorithm（默认，S1/S4/S5/Q1）       │  │
│  │   └─ FirstFitAlgorithm（备选）                        │  │
│  ├──────────────────────────────────────────────────────┤  │
│  │          ▼ AllocationOutcome                          │  │
│  │ 后优化器层（可选，SPI）★v1.2 新增                      │  │
│  │   interface PostOptimizer（§5.2b）                    │  │
│  │   └─ CrossFactorySwapOptimizer（默认，含熔断）          │  │
│  ├──────────────────────────────────────────────────────┤  │
│  │          ▼ AllocationOutcome（终态）+ OptimizationStats│  │
│  └──────────────────────────────────────────────────────┘  │
├────────────────────────────────────────────────────────────┤
│ 结果层（算法无关）                                           │
│   P5 结论计算 / 报表 CSV / result.json / 桑基图              │
└────────────────────────────────────────────────────────────┘
```

**隔离原则：**

1. **业务模型层不认识任何具体算法/优化器**——P1/P2 只产出 `SimulationContext`，不含任何"选哪台设备/什么顺序/是否交换"的决策。
2. **算法层与优化器层不接触 CSV 与主数据**——只消费契约对象、只返回契约对象；不得读文件、不得改主数据。
3. **结果层不认识任何具体算法/优化器**——只消费 `AllocationOutcome`（+可选 `OptimizationStats`）；换算法/换优化器后所有输出自动适配。
4. **硬约束归平台，策略归算法**——C5/C6 由 `CapacityAccount` 强制，任何算法/优化器无法绕过（`release` 仅允许释放已有占用且不低于 0，防越界）；"选哪台设备、Lot 顺序、工厂优先、缺口是否回退、是否交换"全部归算法/优化器策略。
5. **契约演进规则**——字段只增不改，旧实现继续可用。

> 编号说明：P1/P2/P5 沿用《业务建模.md》流程编号且固定在平台层；原 P3（排序）与 P4（分配）为算法内部步骤；**交换优化为新增的后优化阶段，不占用 P 编号**（它是策略插件，非必经流程）。

### 5.1 统一契约①：SimulationContext（业务模型层 → 算法层/优化器层）

```java
public record SimulationContext(
    YearMonth yearMonth,                        // 演算月份
    List<Lot> lots,                             // 原始 Lot（未排序——顺序属于算法策略）
    List<ProcessDemand> demands,                // 工序需求清单（含静态候选设备集合）
    Map<String, CapacityAccount> capacity,      // 初始设备账本（剩余=可用）
    Map<String, String> equipmentToArea,        // 设备→区域（只读，派生自设备表）
    Map<String, String> areaToFactory,          // 区域→厂区（只读，派生自设备表）★新增
    Map<String, Integer> factoryOrder,          // 厂区→优先序排名（factory_code 升序派生）★新增
    Map<String, Integer> calendarMinutes        // 演算月日历分钟
) {}
```

约定：

- Context 在每次演算时一次性构建，本次演算内对算法/优化器独占；不跨批次复用。
- `demands` 候选集合为静态过滤结果（C3 ∩ C4）；动态产能校验由 CapacityAccount 强制。
- 工厂优先**不**在 Context 中预排序——算法自行按 `factoryOrder` 分组遍历（S5 是默认算法的策略，见 §5.5）。

### 5.2b 后优化器 SPI：PostOptimizer（★v1.2 新增）

```java
public interface PostOptimizer {
    String name();                                   // 注册名，如 "swap"
    String description();
    boolean shouldRun(AllocationOutcome initial);    // 触发条件（默认：存在缺口 Lot）
    AllocationOutcome optimize(SimulationContext ctx, AllocationOutcome current,
                               OptimizationBudget budget, OptimizationStats stats);
}

public record OptimizationBudget(long deadlineEpochMillis) {   // 熔断预算
    public boolean expired() { return System.currentTimeMillis() >= deadlineEpochMillis; }
}

public final class OptimizationStats {            // 过程统计（优化器填充，结果层展示）
    private long startMillis, endMillis;
    private int iterations, movesTried, movesKept, movesDiscarded;
    private int gapLotsBefore, gapLotsAfter;
    private boolean breakerTripped;               // 是否因熔断提前终止
    // getters / setters
}
```

引擎编排（SimulationEngine）：

```
context = P1 + P2 构建
outcome = algorithm.allocate(context)                       // 阶段：ALLOCATING
if optimizer 启用 && optimizer.shouldRun(outcome):
    budget = OptimizationBudget(now + config.optimizerTimeoutMillis)   // 默认 180000ms
    outcome = optimizer.optimize(context, outcome, budget, stats)      // 阶段：OPTIMIZING
conclusion = P5(outcome, stats)                             // 阶段：REPORTING
```

**熔断保证（平台职责）**：引擎在预算截止后**必须**拿到一个合法 Outcome——优化器实现规则：每轮迭代前检查 `budget.expired()`，熔断即返回**当前已应用的最优快照**（best-so-far），绝不返回半修改状态（迁移采用"试算副本 → 通过则提交"模式，中断天然无损）；另有引擎守护兜底：超预算 +5s 仍无返回则取初始 Outcome 输出。

### 5.5 默认算法实现：BestFitGreedyAlgorithm（算法层）

> 实现已确认策略组合：**S5 工厂优先** + S4 排序 + S1 Best-Fit + Q1 不回退。输入=SimulationContext，输出=AllocationOutcome。

#### 内部步骤一：Lot 排序（S4/Q5）

```
排序键（依次）：
  1. priority 降序                    // C7 粗优先级
  2. qty_lots  降序                   // 大 Lot 先排（默认方向，可配置）
  3. lot_no    升序                   // 保底，保证可复现
排序后列表即分配顺序；不做抢占（先到先得）。
```

#### 内部步骤二：逐 Lot 逐工序"工厂优先 + 组内 Best-Fit"分配（核心，S5+S1）

```
equipmentAccounts : Map<设备, CapacityAccount>   // 来自 ctx.capacity
allocationRecords : List<AllocationRecord>
gapLots           : List<GapLot>

for lot in sortedLots:
  lotFailed = false
  for demand in demandsOf(lot):                     // 按 seq 升序
    if lotFailed: break                             // 前序判缺口则停止（Q1 不回退）
    // ---- S5 工厂优先：候选设备按所属厂区 factory_code 升序（= 优先序）分组 ----
    groups = demand.candidateEquipments
             .groupBy(e -> factoryOrder[areaToFactory[equipmentToArea[e]]])
             .sortByKeyAsc()
    // ---- 逐工厂组尝试：先用尽第一工厂，再第二、第三…… ----
    best = null
    for group in groups:                            // 工厂序小者先
      inGroup = group 中 acct.remaining() >= demand.demandMinutes 的设备   // C6 整Lot
      if inGroup 非空:
        best = inGroup 中 remaining() 最小者        // S1 组内 Best-Fit（榨干）
        break                                      // ★本工厂可容纳即不再看后续工厂
    if best != null:
      equipmentAccounts[best].tryOccupy(demand.demandMinutes)
      allocationRecords += ALLOCATED(lot, demand, best)
    else:
      reason = demand.candidateEquipments.isEmpty() ? "无可加工设备" : "产能不足"
      gapLots += GapLot(lot, demand.process, reason)
      allocationRecords += GAP_LOT_STOP(lot, demand, equipment="-")
      lotFailed = true                              // 不回退（Q1/S2）
```

要点：

- **S5 工厂优先**：候选按厂区 `factory_code` 升序（即优先序，§3.1④ 约定）分组遍历；**第一工厂（编码最小）能容纳就绝不动用第二工厂的产能**——逐 Lot 榨干低序工厂，实现"先一厂、再三厂"。工厂组**内部**仍按 S1 Best-Fit 选剩余最小者，设备不设优先级（Q3）。
- 工厂序由编码升序唯一确定；设备→区域→工厂映射来自设备表单行字段（V11 保证区域不跨厂区）。
- 其余决策（Q1/Q2/Q4/Q6 语义）与 v1.1 相同：不回退、无时序、无区域硬上限、无候选统一缺口。

### 5.6 默认后优化器：CrossFactorySwapOptimizer（★v1.2 新增）

**触发条件（shouldRun）**：初始 Outcome 存在缺口 Lot 且配置开启（`optimizerEnabled=true`）。

**业务语义**：在满足全部硬约束（工序-设备对应 C3、区域准入 C4、整 Lot C6、产能上限 C5）前提下，**推翻部分已完成分配**，把已分配在"卡住缺口 Lot 的工厂/设备"上的 Lot 迁移到其他工厂的富余设备上，腾出产能让缺口 Lot 补入——即"工厂间 Lot 交换"。

**迁移单元（proposal）定义**：

```
proposal = { lot L, 工序 P, 迁出设备 e1(厂X), 迁入设备 e2(厂Y≠X) }
约束：
  - e2 ∈ L 的工序 P 的候选设备集合（C3/C4 静态过滤结果）
  - e2 剩余产能 ≥ L 在 P 的需求分钟（C6，经 tryOccupy 校验）
  - e2 所在工厂 ≠ e1 所在工厂（跨工厂才叫交换；同厂迁移无意义）
```

**评分公式（v1.2.1 按业务更新）**：

```
score = 优先级 × 迁出工厂释放的分钟 − 迁入工厂占用的分钟
      = P × (e1 所在厂 X 因迁出 L 而释放的分钟数)
        − (e2 所在厂 Y 因迁入 L 而新占用的分钟数)

其中 P = 本次迁移所服务的缺口 Lot G 的优先级
      （提案枚举以 G 为锚点；一次迁移连带补入多个缺口 Lot 时，取其中最高优先级）
```

**公式语义解读（两点）：**

1. **优先级的取值对象（暂定，待业务确认）**：P 取**被救援缺口 Lot G** 的优先级——释放的产能价值由它服务的对象决定：为高优先级缺口 Lot 腾挪产能的迁移更值得保留；P=1 时为优先级 1 的缺口做的腾挪得分趋零（自动忽略无谓换位）。若业务意图是**迁出 Lot L 自身**的优先级，仅需改实现中一处常量，契约不变。
2. **判别力说明（v1.2 的"score≡0"问题就此缓解）**：在"加工时间与设备/工厂无关"的现模型下（§3.1⑥），释放分钟 = 占用分钟 = L 的迁移分钟 m，故 **score = (P−1) × m**——P=1 时恒 0，P≥2 时为正且随腾出的产能块大小增长。若未来加工时间按厂区区分，公式将同时反映厂间效率差异。

**接受/舍弃规则（score 决定保留/舍弃，缺口减少为业务主目标）**：

```
试算（在 Outcome 副本上）：
  1. 迁移：release(e1, L分钟) → tryOccupy(e2, L分钟)
  2. 补分配：按原排序序重试所有缺口 Lot（每 Lot 全工序重走 §5.5 分配逻辑）
     —— 补入的 G 仍全部经 tryOccupy 记账，硬约束自动生效
评分与决策（按序判定）：
  if 试算后缺口Lot数 < 当前最优缺口Lot数          → 保留（业务主目标，优先于公式）
  elif 试算后缺口Lot数 == 当前 且 score > 0        → 保留（公式判据：为高优先级缺口的布局腾挪）
  else（缺口增加，或 score ≤ 0 且缺口未减少）      → 舍弃，回滚副本
候选排序：同轮 proposals 按 score 降序逐个试算（高分迁移先试，首改进贪心）
防振荡：同一 (Lot, 工序) 全程最多被迁移 2 次；
        迁入过的工厂记入该 Lot 的"来路"集合，禁止再迁回（防 A→B→A 来回换位）
```

**迭代框架（含熔断）**：

```
budget = now + 180_000ms（config.optimizerTimeoutMillis，默认 3 分钟）
best = initialOutcome；gapBefore = gapCount(best)
loop:
  if budget.expired(): breakerTripped = true; break        // 熔断：返回 best
  proposals = 枚举候选迁移（见下）；枚举中每 64 个检查一次 budget
  if proposals 为空: break                                  // 无可改进，正常收敛
  对 proposal 逐个试算，选**首个被"保留"者**应用到 best       // 首改进贪心
  if 本轮无任何 proposal 被保留: break
  iterations++；更新 stats（movesTried/Kept/Discarded、gapLotsAfter）
return best + stats
```

**候选迁移枚举（每轮，规模受控）**：

```
对每个缺口 Lot G（按优先级降序；reason="无可加工设备"者跳过——无候选可交换）：
  对 G 卡住工序的每台候选设备 e1（当前无法容纳者，厂 X）：
    对 e1 上当前已占用的 (Lot L, 工序 P) 记录
      （迁出候选，按占用分钟降序，每台设备最多取前 5 个）：
      对 L 的工序 P 的候选设备 e2（其他工厂、剩余 ≥ 需求）：
        迁入目标取该厂内"剩余最大"者（吃富余不吃紧）
        生成 proposal(L, P, e1→e2, 锚定 G)   // G 即评分公式中 P 的取值来源
                                            // 单轮 proposal 总量上限 200，超限截断
```

**熔断三道防线**：

1. 优化器逐轮/批量检查 `budget.expired()`，熔断即返回 best-so-far（副本提交模式保证无半状态）；
2. 引擎守护兜底：`budget + 5s` 仍无返回 → 取**初始 Outcome** 兜底输出，优化器结果作废；
3. Node 层：Java 子进程总超时 10 分钟强杀（`child.kill`），页面报错而非无限等待。

> 无论如何，**引擎保证总有合法结果输出**——熔断只是放弃继续改进，不放弃输出。

| V02 | 错误 | FK 完整：routing/equipment/area_eligibility/lots/process_time 等引用链存在 |
| V03 | 错误 | 每品种 ≥1 条路由；seq 无重复 |
| V04 | 错误 | 工艺路线每道工序均有加工时间记录 |
| V05 | 错误 | 数值域：qty_lots>0、priority≥1、minutes_per_lot>0、0<attendance≤100 |
| V06 | 警告 | due_date 缺失/非法（忽略该字段） |
| V07 | 警告 | 品种无 area_eligibility 记录 → 按全区域允许 |
| V08 | 警告 | (品种,工序) 候选设备为空（含区域过滤后为空）→ 将按缺口处理 |
| V09 | 警告 | 未被引用的工序/路线工序无设备对应（主数据可能不全） |
| V10 | 警告 | 设备不在任何 process_equipment 中（将永远闲置） |
| V11 | 错误 | ★设备表内同一 area_code 对应唯一 factory_code（区域不跨厂区，§3.1④ 合并表的跨行一致性） |
| V12 | 警告 | ★某厂区编码无任何设备（该工厂产能恒为 0） |
| V13 | 警告 | ★area_eligibility 引用的 area_code 在设备表中未出现（该准入记录永不生效） |

规则：存在**错误** → 阻断并逐条列出（含 CSV 行号）；仅**警告** → 列出后继续。

## 8. Web UI 交互设计（★v1.2 全面替换命令行 REPL）

### 8.1 架构与职责

```
浏览器 (index.html, 原生 JS + ECharts CDN)
   │  HTTP / 轮询(500ms)
   ▼
Node server.js（内置 http 模块，无 npm 依赖）
   │  child_process.spawn → Java 批处理 CLI
   ▼
Java Main --run --month 2026-11 --algo bestfit [--no-opt] --out output/run_xxx
   │  写 progress.json（阶段/优化计时）→ 写 result.json + 各 CSV/HTML
   ▼
Node 轮询读取 run 目录文件 → 返回给页面
```

- **任务模型**：同一时刻最多 1 个运行中任务（并发请求返回 409 + 当前任务状态），Demo 不做队列。
- **Java 批处理 CLI 参数**：`--run`、`--month yyyy-MM`、`--algo <name>`、`--no-opt`（关闭优化器）、`--out <dir>`、`--validate`（仅校验）。交互式 REPL 已移除（v1.2），CLI 仅保留批处理模式供联调/自动化测试。
- CSV 修改直接用 Excel 编辑保存即可——每次 run 前新起 Java 进程，天然重读最新数据。

### 8.2 REST API（server.js）

| 方法/路径 | 说明 |
|---|---|
| `GET /` | 返回 index.html |
| `GET /api/config` | 算法列表、优化器默认开关、优化超时（180s）、可选月份 |
| `POST /api/run` | body `{month, algo, optimizerOn}` → 启动 Java 子进程，返回 `{jobId, outDir}`；忙时 409 |
| `GET /api/status/:jobId` | 读 progress.json：`{phase, detail, optimizeElapsedMs, iteration, gapLotsCurrent, exitCode}` |
| `GET /api/result/:jobId` | 读 result.json（DONE 后可用） |
| `GET /api/log/:jobId` | Java 子进程 stdout 尾部 200 行（排障） |
| `GET /output/:jobId/:file` | 输出目录静态文件（sankey.html 等） |
| Node 兜底 | Java 进程总超时 10 分钟强杀 → status 置 ERROR |

### 8.3 页面设计（index.html 单页四区）

**① 控制区**（顶部）
- 演算月份（默认当月）、算法下拉（bestfit / firstfit…）、优化器开关（默认开，标注"最多运行 3 分钟"）、[开始计算] 按钮

**② 进度区**（运行中显示）
- 阶段流水灯：加载数据 → 需求展开 → 产能计算 → 分配 → **交换优化** → 生成报表
- 优化阶段实时计时器（**"交换已进行 mm:ss.s"**，来自 progress.json 的 optimizeElapsedMs）
- 熔断状态条：达到 180s 时黄条提示"已达熔断上限，正在输出当前最优结果"；Node 兜底超时红条报错

**③ 结果区**（DONE 后渲染 result.json）
- **结论卡**：总需求/可完成/缺口 Lot 数、结论（富余/缺口）、富余分钟（有富余时）、优化前后对比（可完成↑、缺口↓）
- **优化摘要卡**：优化进行了多久（elapsedMs → mm:ss）、迭代轮数、迁移试/保/舍、缺口改善（前 → 后）、是否熔断
- 缺口四维明细表（品种/工序/区域/设备，tab 切换）
- 利用率表：设备/区域/工厂（tab 切换，瓶颈行高亮）
- 优先级达成分析表
- 桑基图（ECharts CDN 渲染 result.json.sankey，节点名工厂后缀开关；图下方"独立打开 sankey.html"链接）

**④ 历史区**（底部，可选）
- 最近 5 次 run 列表（批次目录、时间、结论、缺口数），点击回看该批 result.json

### 8.4 交互时序

```
[开始计算] → POST /api/run → jobId
页面 setInterval(500ms) → GET /api/status/:jobId
   ALLOCATING → 显示"分配中"
   OPTIMIZING → 优化计时器实时跳动（"交换已进行 00:45.3"）
   DONE       → 停轮询 → GET /api/result/:jobId → 渲染全部结果区
   ERROR      → 停轮询 → 显示错误 + [查看日志]
```

## 12. Demo 阶段明确不做的事（防止范围蔓延）

- 不做数据库、登录/多用户/权限、并发任务队列（单任务 409）
- 不做日/班次粒度排程、物料/人力约束（业务边界外）
- 不做性能优化（数据量级：Lot ≤ 数百、设备 ≤ 数十、迁移枚举已限流）
- 优化器不做全局寻优/精确算法（首改进贪心 + 熔断即止）；多起点/回溯寻优留作未来 PostOptimizer 实现
- 不做配置持久化（CSV 即配置；优化超时等参数写死代码常量）
- 不做 Web 安全（仅本机 127.0.0.1 监听，不暴露公网）
- 交互式命令行 REPL 已移除（v1.2），Java CLI 仅保留批处理模式供自动化

**待业务确认项（v1.2 更新）：**

1. **交换打分公式（v1.2.1 已按业务更新）**：`score = 优先级 × 迁出释放分钟 − 迁入占用分钟`。
   - 优先级取值对象暂定 = **被救援缺口 Lot G 的优先级**（备选：迁出 Lot L 自身优先级，实现中一处常量可切换，契约不变）——待确认。
   - 现模型下 score = (P−1)×迁移分钟：P=1 恒 0（自动忽略为优先级 1 缺口的无谓腾挪），P≥2 为正——公式具备判别力。
   - "score>0 但缺口未减少"的**布局型迁移**是否允许保留（当前设计：允许，作为后续轮次改进的铺垫，配合防振荡规则）——联调时可观察关闭效果。
2. 区域可加工性缺省 = 全区域允许（沿用 v1.1 约定）。
3. 迁入设备选择"剩余最大者优先"（吃富余）是否合理，可在联调中换"组内 Best-Fit"对比。
4. **工厂优先序 = factory_code 升序**（v1.2.2 设备单表合并后不再设 sort_no；编码即序号）——若存在非字典序需求，需在设备表恢复一个厂区优先序字段或约定带序编码。
5. 工厂利用率为新增汇总口径（区域/设备口径不变），报表呈现位置待反馈。
